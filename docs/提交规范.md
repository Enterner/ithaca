# ithaca 提交规范（git commit message 单一事实源）

> 语言与全仓文档一致：**中文**。本规范约束提交信息的结构与措辞；何时可提交
> （check 全绿、用户许可）见 AGENTS.md 边界，不在本文重复。

## 总原则

1. **提交信息讲给半年后的读者**：他只有 `git show` 里的 diff 和这条信息。写清
   「解决了什么问题、为什么必须这么改」，不写工作过程的叙事（"审查第 N 轮发现"
   "评测 v3 跑分 9/9"——轮次/方案/评测是过程产物，文件不是常态存在，随 git 历史漂走，
   提交信息里只留结论）。
2. **一条提交一个主题**。按种类归组（并发修复、数据完整性、诊断基建、文档……），
   同类改动合一笔提交；跨种类的混合批次拆开分别提交。拆分以「单独 revert 是否合理」
   为判据：合理才能同笔。
3. **第一句 = 结论**。不写「修复了一些问题」「优化若干」——点名到行为级
   （"粘贴大文档被拒"、"长思考轮被掐死"、"断线后永久失联"），让读历史的人
   不展开 diff 就知道这笔改了什么症状。
4. **只讲重点，不逐文件流水账**。diff 自己会说改了哪些文件；信息里说的是 diff
   看不出来的部分：动机、根因、取舍、踩过的坑。

## 结构

```
<主题种类的祈使句概括>：<问题 1>；<问题 2>；……
```

- **开头**：一个短语点明主题种类（如「进程与并发修复」「编辑事务防外部改动覆盖」
  「前端 SSE 断线自愈」），后接全角冒号。
- **主体**：分号分隔的要点串。每要点自成一个可读单元：
  - 症状先行（用户可见的行为），根因随后（技术原因，用 ⇒ 或括号衔接）；
  - 关键修复手段一句话带过（"写盘前逐文件核对现盘"、"改两段式"），
    不展开实现细节（diff 可查）。
- **不写**：轮次号/方案名/评测编号/文件清单/「check 全绿」（提交前提，不是内容）。

## 分寸

- **一行可到很长**：中文无强制折行，要点串写满一行是常态（对标 git log --oneline
  可读性——每条自含，不依赖上下文）。
- **测试/验证结果不进提交信息**：能提交即已验证通过；复现过程、轮数、得分属于
  过程数据，留工作日志，不留 git 历史。
- **模型名/平台名等具体环境因素**只在它们是根因的一部分时写（如"某模型流式末块
  无 usage 导致崩溃"——这时模型形态就是问题本身），否则泛化为"部分模型/外部改动/
  特定时序"。
- **防御性代码与误报**：清退比保留优先——防不存在状态的代码连同其错误注释一起删；
  若留下有价值的结论（线程模型、不变式），落成代码旁的 NOTE 而非提交信息。

## 正例（摘自近期历史）

- `进程与并发修复：命令超时/停用改进程树整杀（cmd 链孙进程存活会滞留条目并留孤儿）；工作区热切与命令执行的并发解引用竞态加原子换装；……`
- `编辑事务防外部改动覆盖：校验与写盘之间文件被外部修改……会被静默覆盖，且撤销快照记错原状（撤销连外部改动一起抹掉）；写盘前逐文件核对现盘与批前原状，不一致零写盘整批拒绝并点名让模型重读后再改`

## 反例

- ✗ `审查循环 R12（workspace 数据完整性）：...` ——方案号/轮次是过程产物。
- ✗ `上下文管理优化批（CSA 评测驱动）：...评测 v2/v3：折叠实弹 9/9×3...check 全绿` ——
  评测编号、得分、check 结论都是过程数据。
- ✗ `修复若干问题；优化代码` ——无行为级点名，读历史的人必须展开 diff。
